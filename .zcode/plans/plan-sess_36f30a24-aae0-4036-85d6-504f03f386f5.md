# pido — Pi Coding Agent 桌面客户端(Rust + GPUI + Ely)实施计划

## Context

为 [Pi Coding Agent](https://github.com/earendil-works/pi)(Node.js CLI 编码智能体)写一个 Rust 桌面客户端,UI 使用 [Ely-GPUI-Components](https://github.com/ELY-Open-Source/Ely-GPUI-Components)(基于 Zed 的 GPUI 框架)。工作目录 `D:\develop\code\pido` 为空,全新项目。

**关键调研结论(决定架构的两点):**

1. **集成方式:RPC 模式**。Pi 官方文档(`packages/coding-agent/docs/rpc.md` 等)明确:对非 TypeScript 宿主,以子进程方式启动 `pi --mode rpc`,通过 stdin/stdout 交换**严格 JSONL 协议**(自定义协议,非 JSON-RPC)。它能提供桌面客户端需要的一切:流式输出(`message_update` 增量)、工具调用可见性(`tool_execution_*`)、运行中转向/中止(`steer`/`abort`)、模型与思考级别切换、会话生命周期(`new_session`/`switch_session`/`get_entries`)。认证由 pi 自己读取 `~/.pi/agent/auth.json`,Rust 端零认证代码,用 `pi auth check` 探测即可。TypeScript SDK 仅限进程内使用,不适用。
2. **Ely 组件库出奇地契合**:`ely-chat`(MessageList/StreamingMarkdown/PromptInput/ThinkingBlock)、`ely-agent`(ToolCallCard/AgentStatus)、`ely-documents`(Markdown 渲染,pulldown-cmark)几乎就是聊天客户端的组件地图;Windows(DirectWrite+wgpu)/macOS/Linux 三平台一等支持;自带 i18n 模块和亮暗主题。风险:项目仅 3 周历史,必须用 git 依赖锁定 rev,gpui-pre 需精确 pin `=0.3.11`,Rust 工具链 1.98+。

**用户已确认:** MVP = 核心聊天客户端;界面中英双语可切换;三平台(Windows/macOS/Linux)同时支持。

## 架构

```
pido/                        # Cargo workspace
├── Cargo.toml               # workspace,成员 crates/*,统一 pin 依赖版本
├── crates/
│   ├── pi-rpc/              # Pi RPC 客户端库(纯 Rust,无 UI 依赖,可单测)
│   │   ├── src/protocol.rs  # serde 类型:命令/响应/会话事件/扩展UI记录
│   │   ├── src/client.rs    # 子进程管理、JSONL 分帧、id 关联、事件广播
│   │   ├── src/sessions.rs  # 扫描 ~/.pi/agent/sessions/**/*.jsonl 发现历史会话
│   │   └── tests/           # 用 mock NDJSON 流回放做协议测试
│   └── pido/                # GPUI 应用
│       ├── src/main.rs      # 引导:gpui_platform::application + Ely Assets/init + 主题
│       ├── src/state.rs     # 应用状态(会话、消息、连接状态),EventEmitter 驱动 UI
│       ├── src/i18n.rs      # 中英文案目录(优先复用 Ely i18n,M0 验证其 API)
│       └── src/ui/
│           ├── app.rs       # 根视图:Ely FocusScope + AppShell 布局
│           ├── sidebar.rs   # 按项目目录分组的会话列表、新建会话
│           ├── chat.rs      # MessageList + 流式渲染 + ToolCallCard + 状态条
│           ├── composer.rs  # PromptInput、发送/转向/中止
│           ├── welcome.rs   # 新会话欢迎页 + 项目目录选择
│           └── settings.rs  # 模型选择、思考级别、主题、语言切换
```

**核心设计决策:**
- **进程模型**:同一时刻一个 `pi --mode rpc` 子进程,工作目录 = 用户选的项目目录;切换会话用 `switch_session` 而非重启进程(MVP 简化)。
- **协议处理**(来自官方 rpc.md 的硬性要求):stdout 用专职线程持续读取(否则管道缓冲满会卡死 pi);按 `\n` 分帧(严禁按 U+2028/2029 切);响应用 `id` 关联而非顺序;`message_update` 增量按 `contentIndex` 缓冲、以 `message_end` 为权威覆盖;`prompt` 的 response 只代表"已接受",完成信号是 `agent_settled` 事件;退出 = 关闭 pi 的 stdin。
- **线程桥接**:RPC IO 用 std::thread + crossbeam channel,经 gpui 后台执行器泵入 UI 事件;不引入 tokio。
- **消息展示**:用户/助手消息 → `MessageBubble`;流式助手文本 → `StreamingMarkdown`;思考过程 → `ThinkingBlock`;工具调用 → `ToolCallCard`(ely-agent)。
- **MVP 对扩展 UI 记录**(`extension_ui_request` 等)只解析记录、不渲染对话框(agent 侧有超时兜底),避免 MVP 范围膨胀。

## 依赖(关键部分)

```toml
[workspace.dependencies]
ely-gpui-component = { git = "https://github.com/ELY-Open-Source/Ely-GPUI-Components", rev = "<M0时锁定>" }
gpui = { package = "gpui-pre", version = "=0.3.11" }
gpui_platform = { package = "gpui-pre-platform", version = "0.3.11" }  # Windows/macOS 默认即可
serde = { version = "1", features = ["derive"] }
serde_json = "1"
crossbeam-channel = "0.5"
dirs = "6"
anyhow = "1"

# pido 应用按目标平台加 Linux 特性:
[target.'cfg(target_os = "linux")'.dependencies]
gpui_platform = { package = "gpui-pre-platform", version = "0.3.11", features = ["wayland", "x11"] }
```

## 实施里程碑

### M0 — 环境与骨架(可运行的空窗口)
1. 验证/安装工具链:Rust 1.98+、Node 22.19+、pi CLI(`irm https://pi.dev/install.ps1 | iex`)、`pi auth login` 后 `pi auth check` 输出 ready。
2. `git init`、建 workspace、按上面依赖模板建两个 crate。
3. 按 Ely 官方 bootstrap 模式(`crates/ely-gallery/examples/docs/start.rs`)写出 `main.rs`:`gpui_platform::application().with_assets(Assets).run(...)` → `ely_gpui_component::init(cx)` → `Theme::set_mode_now(Dark)` → `cx.open_window` → 根视图 `FocusScope::new(&focus).root()`,尺寸 1280×820、最小 880×560。
4. **验收**:Windows 本机 `cargo run` 出窗口;三平台 `cargo check` 通过(为尽早暴露平台差异,CI 矩阵从 M0 就建)。

### M1 — pi-rpc 库(无 UI,全单测)
1. `protocol.rs`:serde 类型,命令含 `prompt/steer/follow_up/abort/clear_queue/get_state/get_messages/set_model/get_available_models/set_thinking_level/get_available_thinking_levels/new_session/switch_session/get_entries/get_session_stats/set_session_name`;事件含 `message_start/update/end`、`tool_execution_start/update/end`、`agent_start/end`、`agent_settled`、`queue_update`、`session_info_changed`、`extension_ui_request` 等。未知字段容忍(不加 `deny_unknown_fields`),为协议演进留余地。
2. `client.rs`:启动/杀掉子进程;`send(cmd) -> oneshot<Response>`(id 关联);事件广播 channel;启动时立即 `get_state` 校验连通。
3. `sessions.rs`:扫描会话目录,解析首行 session 头(id/cwd/timestamp)+ `session_info` 名称,按项目目录分组;不依赖 pi 命令(pi 没有 `sessions list`)。
4. **验收**:`cargo test -p pi-rpc` 通过——用一个读取 fixture NDJSON 行回放的假双工流驱动 client;另写一个示例 bin 用真实 `pi` 跑通"发 prompt → 收流式事件 → agent_settled"。

### M2 — 核心聊天 UI(端到端闭环)
1. `state.rs`:AppState(连接状态、当前模型/思考级别、消息缓冲、会话列表),gpui `EventEmitter`,RPC channel 消费循环用 `cx.spawn` 挂到后台。
2. `app.rs` AppShell:左侧 Sidebar(项目分组会话列表 + 新建按钮)+ 主区域;`welcome.rs`(选择项目目录 → 启动 pi + `new_session`)。
3. `chat.rs`:消息流渲染(见"核心设计决策");状态条显示模型名、思考级别、token/成本(usage 事件累计)、连接状态;`agent_settled` 后从 `get_session_stats` 刷新。
4. `composer.rs`:Enter 发送;运行中输入提供 转向(steer)/追加(followUp)切换;Esc = `clear_queue` + `abort`(官方推荐的 Esc 语义);粘贴图片 → base64 `images` 字段(若时间紧可留到 M3)。
5. `settings.rs`:`get_available_models` 驱动的模型选择器、思考级别选择、亮暗主题切换、中英语言切换。
6. **验收**:手动 E2E——新建会话 → 发"列出当前目录文件" → 看到流式文本 + bash 工具卡片 → settled → 运行中再次发消息验证 steer → Esc 中止;切换模型/思考级别立即生效。

### M3 — 会话管理与打磨
1. 恢复历史:`switch_session` + `get_entries` 全量加载;`since` 游标做增量同步;会话重命名(`set_session_name`)。
2. 自动滚动贴底 + `ScrollToBottomButton`;长会话性能检查(gpui 虚拟列表)。
3. 错误与引导面:未安装 pi → 指引安装;`pi auth check` 非 ready → 指引登录;进程崩溃 → 重连/重启会话。
4. 设置持久化(窗口尺寸、主题、语言、最近项目)到 `dirs::config_dir()`。
5. 三平台体验:macOS 原生标题栏 vs Windows 自定义标题栏(`TitlebarOptions` 按平台分支);Linux 验证 wayland/x11 都能起窗口。
6. **验收**:重启应用后能从侧栏恢复上次会话并继续对话;三平台 CI 全绿。

### M4 — 发布准备
1. `cargo clippy --workspace`、`cargo test --workspace`、`cargo fmt` 干净。
2. GitHub Actions 三平台矩阵构建;发布产物:Windows zip/MSI、macOS .app、Linux AppImage(从 cargo-bundle/cargo-wix 里选最省事的,以三平台 `cargo build --release` 产物为底线)。
3. README(双语):截图、安装、pi 前置条件说明。

## 验证方式

- **每里程碑**:`cargo check/clippy/test --workspace` + CI 三平台矩阵。
- **M1 协议层**:mock 流回放单测(不依赖真实 pi/API key)。
- **端到端**(需本机已装 pi 且 `pi auth check` ready):`cargo run -p pido` → 新建会话于临时目录 → 发送任务 → 验证流式输出、工具卡片、steer、abort、模型切换、会话恢复(重启应用)。
- **交叉验证参考**:pi npm 包里的 `RpcClient`(官方参考实现)可对照 Rust 实现的行为语义。

## 风险与对策

| 风险 | 对策 |
|---|---|
| Ely 库很新(3 周)、单维护者、API 未稳定 | git 依赖锁 rev;组件不可用时降级到 ely-core 原语(Button/TextField/List 自绘组合) |
| gpui-pre 版本漂移破坏构建 | 精确 pin `=0.3.11`,升级视为显式变更 |
| pi RPC 协议随版本演进 | 协议类型容忍未知字段;M0 记录本机 pi 版本,以该版本文档为准 |
| Ely i18n API 不确定 | M0 时验证;不满足需求则 `i18n.rs` 自带轻量 catalog(几十条文案,成本很低) |
| 三平台同时支持的工作量 | CI 矩阵从 M0 贯穿;平台特定代码全部 cfg 隔离 |

**范围外(明确不做,留待后续迭代)**:扩展 UI 原生对话框(权限审批)、bash 面板、内置终端、diff 审查、checkpoint 回溯、多 pi 进程并发。
